Memory ledger

显存不是一笔账，而是四笔

权重通常是固定底座；KV 随全部活跃 token 增长；工作区随单轮 prefill/batch 峰值变化；运行时预留则由引擎和 kernel 决定。

模型权重

参数量 × 平均存储字节。量化格式还包含 scale、zero-point、packing、padding 与未量化层。

KV Cache

每 token 的 K/V 状态 × 所有活跃 token。它会随上下文、输出长度和并发持续增长。

激活与工作区

Prefill 激活、Attention/GEMM workspace、logits、采样和临时 tensor。峰值常由单轮 token 数决定。

运行时预留

CUDA context、CUDA Graph、NCCL、allocator 碎片，以及 LoRA、draft model、视觉编码器等附加模块。

M_weights = parameters × bits_per_weight ÷ 8
权重格式理论字节/参数70B 理论大小提醒
BF16 / FP162.0130.4 GiB容量最大，精度稳定
FP8 / INT81.065.2 GiB速度取决于硬件和 kernel
INT4 / W4A160.532.6 GiB另加 scale、元数据和高精度层
B_KV/token = 2(K+V) × L × H_kv × D_head × bytes(KV dtype)

多个请求长度不同，所以总 KV 更准确地写成 M_KV = B_KV/token × Σ Tᵢ。这里的 Σ Tᵢ 就是所有活跃请求实际缓存 token 的总数；如果有 B 个等长请求，每个 T 个 token，它才简化为 B × T。

Paged Attention 会减少碎片并按 block 动态分配，但不会改变一个有效 KV token 的理论字节数。Prefix cache 能让相同前缀只保存一次，因此物理占用更接近“唯一 KV pages 数”。

Attention fundamentals

Hq、Hkv、Dhead 到底是什么

Head 不是把原始 hidden state 复制多份，也不是直接切片；它是对完整 hidden state 做不同的可学习投影，再 reshape 成多个较小向量。

从 hidden state 到多个 heads

X · [N, D_model]
WQ
→
Q · [N, Hq, Dhead]
WK / WV
→
K/V · [N, Hkv, Dhead]
Attention heads → concat → Wo → [N, D_model]

常见设计令 Hq × Dhead = Dmodel，因此 Dhead = hidden_size / Hq；但这是架构选择，不是数学定律。更一般地，Dhead = Q projection 总宽度 / Hq。

GQA：多个 Q heads 共享 KV

Q1Q2Q3Q4Q5Q6Q7Q8
KV 1 · 服务 Q1–Q4KV 2 · 服务 Q5–Q8

MHA：Hq = Hkv。GQA：1 < Hkv < Hq。MQA：Hkv = 1。Llama 3.1 70B 使用 Hq=64、Hkv=8，因此每 8 个 Query heads 共享一组 K/V。

Attention(Q,K,V) = softmax(QKᵀ / √Dhead) V

为什么是 O(N²)

每个 Query token 都要与 N 个 Key token 交互，共有 N×N 个 token pairs。QKᵀ 约需 2N²D FLOPs，后面的 Attention·V 也约需 2N²D FLOPs。Causal mask 只减少常数，不改变 O(N²)。

GPU 会改变复杂度吗

CPU/GPU 上 GEMM 的算术工作量都约为 2MNK FLOPs。GPU 通过更多并行单元和 Tensor Core 降低实际时间，但没有消除工作量。实际性能还取决于利用率、HBM IO、shape 对齐和 kernel launch。

FlashAttention

通过 tiling 避免把完整 N×N score 矩阵写回 HBM，大幅减少 IO 和中间内存；dense attention 的算术复杂度仍近似 O(N²D)。

Prefill vs Decode

完整 prefill 的 dense attention 是 O(N²)。KV Cache 下，单个新 token 只产生一个 Query，与 N 个历史 Keys 交互，所以单个 decode step 是 O(N)；连续生成 N 个 token 的总和仍是 O(N²)。

Parallelism

谁切容量，谁引入通信

并行度不是简单相乘。Attention、dense MLP、MoE experts 可能使用不同网格；回答时要说清每一块内存由哪个维度切分。

TPTensor Parallel

一层内部切矩阵或 heads。降低每卡权重，但每层需要频繁 collective。

PPPipeline Parallel

按层切 stage。适合极大模型和跨节点，但有 stage 传输与 bubble。

DPData Parallel

复制模型副本，处理不同请求。扩总吞吐，但不解决单副本放不下。

EPExpert Parallel

把 MoE experts 分到不同 GPU。分摊专家权重，引入 token all-to-all。

CPContext Parallel

切序列/上下文维度。可分摊超长上下文状态，但 attention 通信复杂。

拓扑原则：TP / EP → 最快的 NVLink/NVSwitch/MNNVL 域；跨节点优先 DP 或较粗粒度 PP

KV offload

用容量换延迟，关键是别搬错数据

热 KV 留在 HBM，冷 page 进入 CPU、NVMe 或远端层；真正的收益来自复用、预取和 KV-aware routing，而不是“把显存扩成无限大”。

GPU HBM最低延迟 · Paged KV
CPU DRAMPCIe / NVLink-C2C
Local NVMe更大容量 · 更高延迟
Remote KV共享缓存 · 网络与路由

权重 offload

每层、每次 forward 都可能把权重搬回 GPU，decode 很容易被 PCIe 带宽限制。

KV offload

只换出暂时不活跃的 pages，并在请求恢复前预取，代价更容易隐藏；若每步都缺页仍会很慢。

最低搬运时间 ≥ bytes_to_move ÷ effective_link_bandwidth

例如搬 10 GiB KV，经 32 GB/s 的有效 PCIe 路径，纯传输下界约 0.31 秒；经数百 GB/s 的 C2C 路径，才可能降到几十毫秒。相关组件包括 LMCache、SGLang HiCache、Mooncake、NIXL、NVIDIA Dynamo 和 TensorRT-LLM KV Cache Manager。

Production validation

理论估算之后，怎么证明它真的能跑

启动成功不等于压力下不会 OOM；平均吞吐很高也不代表 P99 能满足在线服务。

固定模型 revision、量化 checkpoint、CUDA/driver、引擎版本和 attention backend。
读取 layers、hidden size、Q/KV heads、head dim、attention 类型和 MoE top-k。
按实际 checkpoint 和加载 profile 校准权重，而不是只看“7B/70B”标签。
从日志获得 input/output length、总活跃 token、并发和 prefix 重复率分布。
分别压测 prefill-heavy、decode-heavy、长上下文、突发并发和混合 workload。
记录峰值显存、KV capacity、TTFT、ITL、吞吐、排队、preemption 和 cache hit。
核对 NCCL 是否走预期 NVLink/IB 路径，没有意外 fallback。
做 30–60 分钟稳态压测，观察碎片、热身、graph capture 和异常请求。
